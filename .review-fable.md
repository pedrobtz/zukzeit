## R1. The article's quantile-error output was not produced by the code as written

**Location:** `vignettes/articles/model-usage.Rmd:113-118`.

**Evidence.** Line 67 binds `model <- zuk_pretrained("Datadog/Toto-2.0-4m")`.
Line 97 calls `zuk_capabilities(zuk_pretrained("amazon/chronos-2"))` but does
not assign the handle. Line 113 then calls `forecast(model, ...)` with
`quantile_levels = c(0.1, 0.123, 0.9)`. `model` is still Toto.

Toto's catalogue entry (`R/catalogue.R:45`) has
`quantile_levels = seq(0.1, 0.9, by = 0.1)`. The pre-flight check in
`R/capabilities.R:350-357` formats the message from `caps$quantile_levels`, so
the real output for Toto would be nine levels ending in `0.9`. The article shows
twenty-one levels ending in `0.99`. That output came from a Chronos-2 handle.

**Impact.** The article states at line 15 that "every output below was produced
by running the code exactly as written". A reader who runs the chunk gets a
different message and stops trusting the rest of the page. On a project whose
own guidelines say metadata must describe executable behaviour, this is the
same category of error.

**Fix.** Make the handle explicit at line 97 and let the later chunks use it.

```r
model <- zuk_pretrained("amazon/chronos-2")
zuk_capabilities(model)
```

Then line 113 is correct as written, and line 147's re-load is a cache hit.
Alternatively keep Toto and replace the output with Toto's actual message, but
the prose at lines 108-110 is about the Chronos-2 set, so the first option
reads better.

**Verify.** Run the chunk after the change and paste the real output. Then
re-read every chunk from top to bottom tracking what `model` is bound to.

## R3. The float32 fallback warns per batch and copies the whole tensor to probe

**Location:** `R/toto-inference.R:23-43`.

**Evidence.**

```r
precision <- tryCatch(
  {
    data$to(dtype = torch::torch_float64())   # full copy, discarded
    torch::torch_float64()
  },
  error = function(e) {
    cli::cli_warn(c(...))                     # fires on every call
    torch::torch_float32()
  }
)
high <- data$to(dtype = precision)             # full copy, again
```

`toto_causal_scaler()` is called once per batch from `toto_predict_batch()`.
With the default batch size of 64 (`R/batching.R:10-11`), a 70-series panel on
MPS produced two identical warnings in my run. A 500-series panel produces
eight. The reference's `warnings.warn` fires once per call site per session
by default, so the port is noisier than the code it mirrors.

Two secondary problems in the same block:

- The probe allocates a float64 copy of the full `(batch, width + horizon)`
  tensor and throws it away. On CPU, where float64 works, every batch pays
  for that copy twice.
- The function header at lines 18-22 says float32 accumulation "drifts visibly
  over a long context". The warning text says forecasts "may differ in the
  last digits". Measured on real weights at 128 points the difference was
  5e-7 relative. Pick one statement and make it true.

**Impact.** The roadmap's release criteria (`.agents/roadmap.md`, "Safe
execution") require inference to be "deterministic and quiet by default". On
Apple silicon, the default device resolves to MPS, so the package's smallest
and most CPU-friendly model is the one that talks the most.

**Fix.** Resolve the dtype per device with a one-element probe, and warn once
per session per device. `cli::cli_warn()` forwards `...` to `rlang::warn()`,
which supports `.frequency` and `.frequency_id`.

```r
# The reference accumulates the causal statistics in float64 and falls back to
# float32 where the backend has no double precision, warning when it does. MPS
# is that case. The probe is one element, and the warning is once per session
# per device, matching Python's default warning filter.
toto_scaler_dtype <- function(device) {
  has_float64 <- tryCatch(
    {
      torch::torch_zeros(1L, dtype = torch::torch_float64(), device = device)
      TRUE
    },
    error = function(e) FALSE
  )
  if (has_float64) return(torch::torch_float64())
  cli::cli_warn(
    c(
      "Float64 is unsupported on device {.val {as.character(device)}}.",
      "i" = "Using float32 for the Toto scaler; forecasts may differ in the last digits."
    ),
    .frequency = "once",
    .frequency_id = paste0("zukzeit_toto_float64_", as.character(device))
  )
  torch::torch_float32()
}

toto_causal_scaler <- function(data, mask, patch, minimum_scale = 1e-6,
                               correction = 1) {
  precision <- toto_scaler_dtype(data$device)
  high <- data$to(dtype = precision)
  keep <- mask$to(dtype = precision)
  ...
}
```

If you want zero per-batch cost, memoise the probe result in a package
environment keyed by `as.character(device)`. The one-element probe is cheap
enough that this is optional.

Rewrite the header comment at lines 18-22 to say: float64 where the backend
supports it, float32 on MPS as upstream does, measured difference on real
weights in the 1e-7 relative range.

**Add a test** to `tests/testthat/test-toto-synthetic.R`. It skips where MPS is
absent, which is every CI runner today, but it runs on the machine where the
bug was found. `rlang`'s once-per-session filter means an earlier test may
already have consumed the warning, so assert at most one rather than exactly
one.

```r
test_that("the float32 fallback warns at most once, not once per batch", {
  skip_if_no_torch()
  skip_if_not(
    isTRUE(tryCatch(torch::backends_mps_is_available(), error = function(e) FALSE)),
    "MPS is not available."
  )
  config <- toto_synthetic_config()
  config$device <- "mps"
  model <- toto_constructor(config, toto_synthetic_weights(config))
  contexts <- replicate(3, cumsum(stats::rnorm(96)), simplify = FALSE)
  seen <- 0L
  withCallingHandlers(
    for (ctx in contexts) model$predict_fn(ctx, 8L, c(0.1, 0.5, 0.9)),
    warning = function(w) {
      seen <<- seen + 1L
      invokeRestart("muffleWarning")
    }
  )
  expect_lte(seen, 1L)
})
```

The existing `expect_silent()` at `test-toto-synthetic.R:70` already covers
the CPU side.

**Verify.** Re-run the 70-series MPS comparison; expect one warning, then none
on a second call in the same session.

## R4. The loader regression test never runs in the every-push tier

**Location:** `tests/testthat/test-lifecycle.R:236-256`.

**Evidence.** The test loops
`for (architecture in zuk_models()$architecture) skip_unless_checkpoint(architecture)`,
so it skips unless every supported checkpoint is enabled. The `parity-small`
job sets `ZUK_RUN_CHECKPOINT_TEST=toto2`, so the test skips there. Confirmed
in the `toto2` run: it is skip 3 of 18 with the message
"Set ZUK_RUN_CHECKPOINT_TEST=timesfm to run timesfm checkpoint tests".

The Toto parity tests build their handle with `toto_constructor()` directly
(`test-parity-toto.R:43`), which is exactly the bypass the commit message
identifies as the reason the bug went unnoticed. So in the `toto2` tier
nothing calls `zuk_pretrained("Datadog/Toto-2.0-4m")` at all. A regression of
the bug this commit fixed would pass `parity-small` and only fail on `main`.

Three smaller rough edges in the same test:

- The skip message names one architecture when all three are needed.
- It does not pin `device = "cpu"`. Every sibling smoke test does and the
  header of `test-smoke-timesfm.R` explains why: the default resolves to MPS
  or CUDA on an accelerator host.
- There is no `on.exit(zuk_unload())`, so a failure mid-loop leaves a large
  handle resident for the tests that follow.

**Fix.** Register one test per supported row at file level, so each tier
exercises its own loader path.

```r
for (index in seq_len(nrow(zuk_models()))) {
  row <- zuk_models()[index, ]
  test_that(sprintf("%s loads through the public loader", row$model_id), {
    # Regression: the port tests construct handles by calling each
    # architecture's constructor directly, which bypasses zuk_pretrained().
    # Deriving the architecture from config.json rather than the curated
    # record left two of three supported checkpoints unloadable through the
    # documented path, and nothing caught it.
    skip_unless_checkpoint(row$architecture)
    skip_if_no_torch()
    on.exit(zuk_unload(), add = TRUE)

    model <- zuk_pretrained(row$model_id, device = "cpu")
    expect_s3_class(model, "zuk_model")
    expect_identical(model$architecture, row$architecture)
    expect_identical(model$model_id, row$model_id)
    expect_identical(model$capabilities$max_context, row$max_context)
  })
}
```

**Verify.** `ZUK_RUN_CHECKPOINT_TEST=toto2` should now show the Toto loader
test passing and the other two skipping with accurate messages.

## S1. `normalize_architecture()` is unreachable and carries wrong aliases

**Location:** `R/hub.R:176` and `R/hub.R:194-218`.

**Evidence.** After this change:

```r
config$architecture <- record$architecture %||% normalize_architecture(config)
```

Every record in `R/catalogue.R` sets `architecture`, and
`zuk_resolve_catalogue_entry()` aborts on any ID not in the catalogue. So the
right-hand side is never evaluated from `zuk_pretrained()`. It survives only
in its own unit tests (`test-architectures.R:9-20`) and one direct call in
`test-state-dict.R:91`.

The alias table also maps `chronos` and `chronosbolt` to `chronos2`. Chronos
and Chronos-Bolt are different architectures with different state dicts. And
the lookup prefers `model_type` over `architectures`; Chronos-2's config
declares `model_type = "t5"`, so even with a `chronos2model` alias added, the
sniffer would return `t5`.

**Impact.** No runtime effect today. The cost is a reader who trusts the alias
table, and a future contributor who adds a Chronos-Bolt entry and gets the
Chronos-2 constructor. The commit replaced one source of truth with another
instead of deciding whether two are needed.

**Fix, recommended.** Delete it. The catalogue is package-owned, revisions are
immutable SHAs, and each constructor already rejects unknown variants
(`validate_toto_config()`, `toto_context_length()`, and their TimesFM and
Chronos-2 counterparts). A second opinion from the config adds nothing that
parity does not already prove.

1. `R/hub.R:176` becomes `config$architecture <- record$architecture`.
2. Remove `normalize_architecture()` and the comment block above line 176.
3. Remove the alias tests at `test-architectures.R:9-20`.
4. `test-state-dict.R:91` becomes `config$architecture <- record$architecture`.
5. Add a catalogue test asserting every record has a non-empty `architecture`
   that `zuk_registry_has()` knows, so the invariant the loader now relies on
   is enforced somewhere.

**Fix, alternative.** If you want defence in depth, keep it as a cross-check
rather than a fallback: prefer `architectures[1]` over `model_type`, add
`chronos2model = "chronos2"`, drop the two wrong aliases, treat a config with
no declaration as "no opinion", and abort with a checkpoint error when the
config disagrees with the catalogue. That is more code for a case immutable
SHAs already rule out, which is why deletion is the recommendation.

## S2. Two copy-pasted parity jobs with hand-copied SHAs

**Location:** `.github/workflows/R-CMD-check.yaml:76-112` and `124-170`.

**Evidence.** The jobs share checkout, R setup, dependency install, LibTorch
install, cache, prefetch, and test steps. They differ in the cache key, the
prefetch list, and one env var. The Toto revision SHA now lives in the
`parity-small` key, the `parity` key, and `R/catalogue.R:42`.

The commit message for `4659644` describes the bug this pattern produces: the
key "had not been kept current", so two checkpoints were downloaded uncached
on every run. Adding a second hand-maintained key doubles the surface for the
same mistake.

**Fix, step one, small.** Derive the key and the prefetch list from the
catalogue in a step, so a revision bump in R invalidates the cache without
anyone editing YAML.

```yaml
      - name: Derive the cache key from the catalogue
        id: key
        run: >
          Rscript -e '
            pkgload::load_all(".", quiet = TRUE)
            tier <- Sys.getenv("ZUK_RUN_CHECKPOINT_TEST")
            m <- zuk_models()
            if (!identical(tier, "true")) m <- m[m$architecture %in% trimws(strsplit(tier, ",")[[1]]), ]
            cat(sprintf("key=hf-%s\n", paste(m$architecture, substr(m$revision, 1, 12), sep = "-", collapse = "-")))
            cat(sprintf("ids=%s\n", paste(m$model_id, collapse = ",")))
          ' >> "$GITHUB_OUTPUT"
        env:
          ZUK_RUN_CHECKPOINT_TEST: 'toto2'

      - uses: actions/cache@v6
        with:
          path: ~/.cache/huggingface
          key: ${{ steps.key.outputs.key }}

      - name: Prefetch the checkpoints
        run: >
          Rscript -e '
            pkgload::load_all(".")
            for (id in strsplit("${{ steps.key.outputs.ids }}", ",")[[1]]) zuk_download(id)
          '
```

**Fix, step two, structural.** Move the shared body into a reusable workflow
`.github/workflows/parity.yaml` with one input, and call it twice.

```yaml
# .github/workflows/parity.yaml
on:
  workflow_call:
    inputs:
      checkpoints:
        description: Value for ZUK_RUN_CHECKPOINT_TEST
        required: true
        type: string

jobs:
  parity:
    runs-on: ubuntu-latest
    env:
      GITHUB_PAT: ${{ secrets.GITHUB_TOKEN }}
      ZUK_RUN_CHECKPOINT_TEST: ${{ inputs.checkpoints }}
    steps:
      - uses: actions/checkout@v6
      - uses: r-lib/actions/setup-r@v2
        with:
          r-version: 'release'
      - uses: r-lib/actions/setup-r-dependencies@v2
        with:
          extra-packages: any::testthat, any::pkgload
          needs: check
      - name: Install the LibTorch runtime
        run: Rscript -e 'torch::install_torch()'
      # ... the derive-key, cache, prefetch steps from step one ...
      - name: Run the checkpoint-gated suite
        run: Rscript -e 'testthat::test_local(".", stop_on_failure = TRUE)'
```

```yaml
# in R-CMD-check.yaml
  parity-small:
    name: numerical parity (small checkpoint)
    uses: ./.github/workflows/parity.yaml
    with:
      checkpoints: toto2

  parity:
    name: numerical parity (pinned checkpoint)
    if: github.event_name == 'workflow_dispatch' || (github.event_name == 'push' && github.ref == 'refs/heads/main')
    uses: ./.github/workflows/parity.yaml
    with:
      checkpoints: 'true'
```

Neither snippet has been run. Validate with a `workflow_dispatch` before
relying on it. Step one alone removes the hand-copied SHAs and is worth doing
even if step two waits.

checkpoint_tests_enabled <- function(architecture) {

  requested <- trimws(strsplit(tolower(requested), ",", fixed = TRUE)[[1]])

## Resolution log

### R5, found while fixing R1: the covariate section scored the model against a biased baseline

Not in the original review. The article claimed the model "recovers a
promotion effect of 121 against a true effect of 117", which reads as a near
perfect match. Running the code showed where 117.2 came from: it is the naive
difference between promotion days and ordinary days.

The series is generated with `150 * promo`, so the true effect is 150 by
construction. Promotions land unevenly across a rising trend and a weekly
cycle, so the naive contrast is biased downwards. A regression conditioning on
both recovers 149.69.

| Estimator | Value |
|---|---|
| Naive difference in means (what the article called "true") | 117.19 |
| Regression on trend, seasonality, and promotion | 149.69 |
| True generating coefficient | 150 |
| Mean lift the model actually produces on promotion days | 121.10 |

So the model recovers about four fifths of the real effect, not essentially
all of it. The section now states that, shows the regression that establishes
the baseline, and warns against the naive contrast. This mattered more than
anything else in the article: it was the page's strongest quantitative claim,
and it was flattering the model by comparing it against a number that happened
to sit nearby.

Two smaller output errors surfaced in the same pass. The capability block
elided Chronos-2's quantile levels as `0.01, 0.05, 0.1, ..., 0.95, 0.99`,
where the real print lists all twenty-one; and both error blocks omitted the
`in \`zuk_infer()\`` / `in \`zuk_run_batches()\`` call attribution that `cli`
actually emits. Both are now the literal output.
