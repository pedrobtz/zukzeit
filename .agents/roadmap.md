# `zukzeit` roadmap

`zukzeit` is an inference engine for running open time-series foundation models
natively in R.

**North star:** given a supported pretrained checkpoint and numeric history,
load the model, run it locally with R `torch`, and return predictive quantiles
through one stable interface.

This roadmap is release-driven. It defines exactly what `0.1.0` means, the
ordered stages required to reach it, and the work deliberately deferred until
after it.

*Last reviewed: 2026-08-23.*

---

## Current status

The engine runs the pinned TimesFM 2.5 and Toto 2.0 4M checkpoints natively,
both passing their architecture-conformance and numerical-parity gates. This is
not yet a `0.1.0` release candidate: the release scope also requires Chronos-2,
which is blocked on the contract-v2 extension. Stage 5 is closed; Stage 6
remains open.

| Architecture | Current state | `0.1.0` role |
|---|---|---|
| `stub` | Works end to end; random-walk test fixture | Keeps engine and adapter tests fast |
| `ttm` | Registered scaffold; forward pass aborts | Deferred: the selected TTM-R2 checkpoint is point-forecasting, not native-quantile |
| `timesfm` | Native R `torch`; conformance and pinned CPU parity pass | **Implemented `0.1.0` general quantile model** |
| `toto2` | Native R `torch`; conformance and pinned CPU parity pass | **Implemented `0.1.0` efficient probabilistic model** |
| `chronos2` | Old Brulee adapter removed; no native implementation yet | **Required `0.1.0` multivariate/covariate model** |

The repository already contains useful foundations:

- an architecture constructor registry behind a package-owned curated
  checkpoint catalogue and Hub configuration resolver;
- capability metadata and pre-flight checks;
- a versioned architecture contract and executable conformance harness;
- panel batching, context truncation, and CPU/CUDA/MPS device resolution;
- a quantile-based `zuk_forecast` object backed by `distributional`;
- plain-R, fabletools conversion, `TSFM()` composition, and tidymodels adapters;
- stub-based tests of the core execution path, plus opt-in real-checkpoint
  smoke tests covering all four user journeys.

The important remaining `0.1.0` gaps are:

- TTM has no weight map, module, or forward pass and remains outside `0.1.0`;
- the current contract cannot carry covariates or multivariate targets;
  contract v2 must add them without breaking contract-v1 consumers;
- Chronos-2 needs a native module, contract-v2 execution path, checkpoint map,
  fixtures, conformance, and numerical-parity certification;
- release hardening must be repeated after both architectures land.

These gaps determine the stages below.

## Goal for `0.1.0`

`0.1.0` is the first useful portfolio proof of the package's premise:

> A user can choose among pinned TimesFM 2.5, Toto 2.0 4M, and Chronos-2
> checkpoints and produce numerically correct zero-shot forecasts locally,
> using native R `torch`, through the plain-R API and the primary R forecasting
> adapters. A downstream package such as `tsai` can discover their distinct
> costs and capabilities, reuse handles, and safely recover around the engine
> through a stable programmatic API.

The three models are complementary: TimesFM is the general quantile baseline,
Toto is the small deployment model, and Chronos-2 proves multivariate targets
plus past and future-known covariates. No checkpoint is supported before both
conformance and numerical-parity gates pass.

### Required user journeys

All four surfaces must work from a clean installation. The example uses
TimesFM; equivalent smoke tests must run for Toto and Chronos-2, with
contract-v2 inputs exercised for Chronos-2:

```r
# Plain R
model <- zuk_pretrained(
  "google/timesfm-2.5-200m-pytorch",
  revision = "<pinned-commit-sha>"
)
fc <- forecast(model, history, h = 12, index = "date", target = "value")
as.data.frame(fc)

# tidyverts
fc |> fabletools::as_fable()

# composable tidyverts model definition
fits <- fabletools::model(
  history,
  timesfm = TSFM(
    value,
    model_id = "google/timesfm-2.5-200m-pytorch",
    revision = "<pinned-commit-sha>"
  )
)
fabletools::forecast(fits, h = 12)

# tidymodels
spec <- zuk_reg() |>
  parsnip::set_engine(
    "zukzeit",
    model_id = "google/timesfm-2.5-200m-pytorch",
    revision = "<pinned-commit-sha>",
    index = "date"
  )
parsnip::fit(spec, value ~ 1, data = history)
```

### Release acceptance criteria

`0.1.0` is complete only when all of the following are true:

- **Native execution:** TimesFM 2.5, Toto 2.0 4M, and Chronos-2 weights are
  downloaded, cached, loaded into R `torch` modules, and evaluated without
  Python or Brulee at runtime.
- **Numerical correctness:** each checkpoint has committed golden fixtures
  generated by a pinned official reference implementation and passes them on
  CPU within a documented `atol`/`rtol` tolerance.
- **Contract conformance:** all three models pass their applicable
  `zuk_check_architecture()` checks, including shape, finite output, monotone
  quantiles, context limits, and batch/loop agreement.
- **Honest scope:** every advertised capability has an executable path.
  Contract v1 remains valid for univariate quantile consumers; contract v2
  represents grouped targets and past/future covariates for Chronos-2.
  Unsupported sample-path, point-only, imputation, and fine-tuning requests
  fail before inference.
- **Usable core:** single-series and panel forecasts work through `forecast()`;
  checkpoint provenance and weight licence are visible on the model handle;
  the offline catalogue, explicit download, bounded handle reuse, cache status,
  and unload APIs satisfy the `tsai` consumer contract.
- **Typed failures:** every public engine error has a leaf class and one policy
  parent so consumers can distinguish fallback, retry-later, and bug outcomes
  without matching message text.
- **Working adapters:** fabletools conversion and a real `parsnip::fit()` plus
  `predict()` pass end-to-end tests; `TSFM()` works inside
  `fabletools::model()`. Optional adapters remain in `Suggests`.
- **Safe execution:** inference is deterministic and quiet by default, responds
  to interrupts between batches, cleans up execution state, and never returns
  a partial forecast.
- **Release quality:** generated documentation exists; examples do not download
  weights during checks; local and GitHub `R CMD check` report zero errors and
  zero warnings; the README describes only features that actually work.
- **Reproducibility:** every supported model ID, checkpoint SHA, configuration,
  fixture generator, expected output, and tolerance is recorded in the
  repository.

CPU inference is the required portability baseline. CUDA and MPS support remain
available through the device abstraction, but accelerator-specific performance
or numerical certification is not a blocker for `0.1.0`.

### Explicitly not required for `0.1.0`

- any fourth supported real model, including TTM, Granite PatchTST-FM,
  Sundial, TiRex-2, or another checkpoint family;
- a Brulee runtime backend;
- point-only output, sample paths, reconstruction/imputation, conformal
  calibration, or reconciliation helpers;
- fine-tuning, LoRA, mixed precision, or distributed execution;
- `modeltime`, recipe, `autoplot()`, or `as_tibble()` adapters;
- a fully declarative shared preprocessing framework; common code is extracted
  only where the three release ports demonstrate genuine duplication;
- CRAN acceptance. The release must be CRAN-ready in quality, but a GitHub tag
  may precede submission.

## Architectural decisions for `0.1.0`

### Three native models define the release

The engine contract promises predictive quantiles. The official
[TimesFM 2.5 model card](https://huggingface.co/google/timesfm-2.5-200m-pytorch)
documents a point forecast plus 10 output channels containing the mean and
0.1–0.9 quantiles. It therefore exercises the package's actual contract without
an invented uncertainty layer.

TimesFM remains the reference implementation and completed baseline. Toto 2.0
4M adds a small, CPU-friendly probabilistic checkpoint without first requiring
a new output type. Chronos-2 adds the release's richer input contract:
multivariate targets and past/future-known covariates with requested quantiles.
Each port owns its native module and pinned parity evidence.

The official
[TTM-R2 model card](https://huggingface.co/ibm-granite/granite-timeseries-ttm-r2)
describes that release as serving point-forecasting use cases. TTM remains a
good future CPU-friendly model, but supporting it honestly requires the engine
to represent point-only output rather than claiming native quantiles.

### Brulee is not a `0.1.0` backend

Brulee remains useful as prior art and as an independent source of Chronos-2
reference behaviour. It is not the implementation foundation for this package:

- `0.1.0` must prove native model ownership inside `zukzeit`;
- an adapter over another high-level R interface obscures the engine boundary;
- the removed wrapper was unverified and had correctness and lifecycle defects;
- using it would expand the release surface without validating the native
  loader or architecture path.

Chronos-2 therefore enters the supported catalogue only through a native
R/`torch` port that passes the same conformance and parity gates as TimesFM.
Until that stage closes, the existing early rejection remains in force and the
README must describe Chronos-2 as planned rather than available.

### Contract v2 extends rather than replaces contract v1

The existing univariate quantile contract remains supported unchanged:

```text
predict_fn(context, h, quantile_levels) -> matrix[h, q]

predict_batch_fn(contexts, horizons, quantile_levels, device)
  -> list(matrix[h, q])
```

Contract v2 adds typed grouped targets and optional past/future covariate
channels for Chronos-2. Existing TimesFM callers and model ports continue to use
contract v1 without synthetic empty inputs. Toto may advertise only the subset
that is implemented and parity-tested. The `samples` capability remains
`FALSE` until the later Sundial stage provides a sample-return channel.

### Adapters stay outside the engine

The core remains usable without hardhat, parsnip, fabletools, tsibble, or
modeltime. Those packages stay in `Suggests`, and adapter failures may not block
package loading or plain-R inference.

### The consumer API is a release contract

The surface in [`consumer-api.md`](./consumer-api.md) is required for `0.1.0`.
`tsai` is a downstream consumer and creates no reverse dependency, but it must
be able to enumerate supported checkpoints offline, prefetch weights, reuse a
constructed handle, branch on classed failures, and use `TSFM()` inside
fabletools. Selection, fallback policy, backtesting, and LLM orchestration stay
outside `zukzeit`.

## Target model catalogue

The catalogue is curated rather than exhaustive. A model belongs on the list
when it is important to users, has official downloadable weights and reference
code, adds a capability or deployment profile not already covered, and can
plausibly be maintained as a native R implementation.

Priority meanings:

- **P0 — release commitment:** a model on the current release critical path;
- **P1 — core target:** an important, permissively licensed family that `zukzeit`
  intends to support;
- **P2 — conditional target:** valuable, but blocked by a contract extension,
  unusual runtime requirements, or restrictive weight terms.

| Priority | Family and canonical checkpoint | Why it matters | Native output | Weight licence | Main blocker |
|---|---|---|---|---|---|
| **P0** | [TimesFM 2.5](https://huggingface.co/google/timesfm-2.5-200m-pytorch) | General quantile baseline with long context | Point plus 0.1–0.9 quantiles | Apache-2.0 | Implemented and certified |
| **P0** | [Toto 2.0 4M](https://huggingface.co/Datadog/Toto-2.0-4m) | Small CPU/edge representative with a scalable probabilistic family | 0.1–0.9 quantiles | Apache-2.0 | Native alternating time/variate attention port and parity fixtures |
| **P0** | [Chronos-2](https://huggingface.co/amazon/chronos-2) | Universal representative for multivariate targets and past/future covariates | Requested quantiles | Apache-2.0 | Contract v2, native group-attention port, and parity fixtures |
| **P1** | [Granite PatchTST-FM R1](https://huggingface.co/ibm-granite/granite-timeseries-patchtst-fm-r1) | Reconstruction representative with dense quantiles and simultaneous missing-value imputation | 99 trained quantiles plus imputation | Apache-2.0 | Reconstruction/masking output contract and 260M native port |
| **P1** | [Sundial / Timer 3.0](https://huggingface.co/thuml/sundial-base-128m) | Generative representative supporting arbitrary statistics from forecast samples | Sample paths | Apache-2.0 | Sample-path contract and flow-matching sampler |

### Support order is not the same as model rank

Implementation order follows contract and porting dependencies:

1. **TimesFM 2.5** proves the current quantile contract in `0.1.0`.
2. **Toto 2.0 4M** completes the efficient probabilistic slot in `0.1.0`.
3. **Chronos-2** completes `0.1.0` after the grouped-target and covariate
   contract extension.
4. **Granite PatchTST-FM** follows with reconstruction and imputation semantics.
5. **Sundial** follows with a sample-path output contract.

Within a family, `zukzeit` supports architecture-compatible checkpoints through
one implementation; it does not create bespoke code for every size or branch.
One small canonical checkpoint supplies CI fixtures, while larger compatible
variants are smoke-tested outside the normal check path.

### Models deliberately outside the catalogue

- Hosted-only services such as TimeGPT: they are API clients, not local model
  engines.
- Granite TTM is not a current target because Toto fills the small local-model
  slot while preserving probabilistic output.
- TiRex-2 is a permissively licensed alternative to Chronos-2, but supporting
  both does not currently justify a second multivariate/covariate port.
- Moirai 2.0 and TiRex v1 are excluded because their checkpoint terms are not
  MIT or Apache-2.0.
- Older generations when a compatible current generation supersedes them,
  unless users demonstrate a reproducible accuracy or deployment reason.
- Fine-tuned community checkpoints: the registry may load compatible variants,
  but `zukzeit` only certifies upstream base checkpoints.
- Models without immutable downloadable weights, reproducible reference code,
  or sufficiently clear usage terms.

The catalogue is reviewed at each minor release. Popularity alone is not enough:
every supported family still needs immutable revisions, licence metadata,
contract conformance, and independent numerical-parity fixtures.

## Stages to `0.1.0`

Stages are sequential release gates, not estimates. A stage is complete only
when its exit gate is executable and green.

| Stage | Outcome | Status |
|---|---|---|
| 0 | Establish an honest, reproducible baseline | **Implementation complete** |
| 1 | Prove TimesFM feasibility; freeze catalogue and error contracts | **Implementation complete** |
| 2 | Build the reference, loader, download API, and handle LRU | **Implementation complete** |
| 3 | Implement safe native TimesFM inference | **Implementation complete** |
| 4 | Prove all four user-facing workflows | **Implementation complete** |
| 5 | Implement and certify Toto 2.0 4M | **Not started** |
| 6 | Add contract v2 and implement native Chronos-2 | **Not started** |
| 7 | Validate all three models and release `0.1.0` | **Blocked on stages 5–6** |

### Stage 3 — Native TimesFM inference

Implement the first real architecture in native R `torch`.

Deliverables:

- implement TimesFM normalization, patching, padding, and output transforms
  required by the pinned checkpoint;
- implement the TimesFM `nn_module` from checkpoint configuration;
- implement and test the safetensors-to-module weight map;
- implement single-series `predict_fn` and vectorized `predict_batch_fn`;
- run modules in evaluation mode with gradients disabled;
- guarantee identical output for repeated calls with the same checkpoint,
  inputs, arguments, and device;
- keep normal inference silent and route explicit progress through a
  suppressible mechanism rather than `cat()`, `print()`, or unconditional
  messages;
- check for user interrupts between batches, run cleanup on exit, do not wrap
  interrupts as model errors, and never return a partial `zuk_forecast`;
- normalize device and dtype handling, with CPU as the required baseline;
- handle short contexts, missing values, truncation, and horizons larger than a
  single model output block explicitly;
- add diagnostic errors for unsupported checkpoint variants or tensor shapes.

Exit gate:

- TimesFM passes both independent gates:
  1. `zuk_check_architecture(timesfm_constructor)`; and
  2. every committed numerical-parity fixture on CPU within tolerance;
- repeated-inference tests are identical and silent, and a simulated interrupt
  leaves no partial result or stale execution state.

No architecture is called supported until both gates pass.

Local close-out on 2026-08-13:

- the pinned 232-tensor checkpoint maps exactly onto a native 20-layer R
  `torch` module; meta-device construction lets the module adopt safetensors
  storage without retaining a second CPU state-dict copy;
- preprocessing and decode implement left padding, cumulative per-patch
  reversible normalization, causal rotary attention, cached 128-value
  autoregressive blocks, the 1,024-value continuous quantile head, flip
  invariance, non-negativity inference, and crossing repair;
- single and vectorized batch paths pass the typical, three-value short,
  16,256-value truncation, and two-series fixtures on CPU within the recorded
  `atol = 1e-4, rtol = 1e-5` budget, the measured worst case being `3.05e-05`
  absolute and `7.33e-07` relative (4 to 12 float32 ulps); exact float32 inputs
  are committed beside the JSON outputs;
- requested quantile levels are reconciled to the checkpoint's trained levels at
  the engine boundary, so the two spellings of `0.1 … 0.9` in circulation — the

  being exact on arm64. The tests assert agreement within the float32 budget,
  which a genuine regression to batch-wide truncation exceeds by four orders of
  magnitude;
- `zuk_check_architecture()` passes all ten applicable checks against the real
  handle; repeated inference is bit-identical and silent;
- unsupported config variants, missing or mismatched tensors, and device/handle
  mismatches fail diagnostically before inference;
- engine batches and autoregressive blocks place explicit interrupt boundaries,
  do not wrap interrupt conditions, and never assemble or return a partial
  forecast. R delivers the interrupt at those boundaries; a single `torch` call
  remains uninterruptible, so the guarantee is where the boundaries sit, not
  that inference polls for them;
- the default deterministic suite passes 324 tests with only explicit optional
  integration skips; the real-checkpoint parity and state-dict suite passes
  locally, with a measured maximum RSS of about 2.53 GB for the combined run.

TimesFM is now `supported` in the offline catalogue. Stage 4 owns proof of the
four public user workflows and remains necessary before the release is closed.

## Engine boundary

The architecture contract is the stable center. Framework integrations are
adapters around it.

```text
optional adapters
  plain R       forecast(), as.data.frame()
  tidyverts     fabletools::as_fable(), TSFM()
  tidymodels    zuk_fit(), zuk_reg()
        |
execution
  validation -> preprocessing -> batching/device -> architecture forward pass
        |
loading
  catalogue -> Hub/cache -> safetensors -> registered architecture -> handle LRU
        |
public contract
  classed errors + capabilities + model handle + quantile forecast + tests
```

Rules:

1. The engine never defines competing ecosystem generics.
2. Optional adapters do not become core runtime dependencies.
3. A model is supported only after conformance and numerical parity both pass.
4. Capability metadata describes executable behaviour, never future intent.
5. Checkpoint revisions used for support claims are immutable commit SHAs.

## Risks and controls

| Risk | Control |
|---|---|
| Port appears plausible but computes the wrong model | Generate fixtures first; require independent parity and conformance gates |
| Checkpoint/config changes upstream | Support immutable SHAs and reject unknown variants explicitly |
| Capability metadata outruns implementation | Test every `TRUE` capability through the public contract |
| R `torch` operator, memory, or dtype gap | Require a TimesFM vertical spike before fixture and full-port work |
| Large downloads make tests unreliable | Commit small outputs, mock cache/error paths, keep Hub smoke tests opt-in |
| Repeated adapter fits exhaust process memory | Bound constructed handles with a one-entry default LRU and expose resident status/unload controls |
| Optional frameworks destabilize the core | Keep adapters in `Suggests` and test core installation without them |
| Documentation gets ahead of code | Every supported-model and workflow claim must map to an executable test |
| CI cannot establish release quality | Do not tag `0.1.0` until GitHub Actions runs and is green |
| Maintenance expands faster than correctness coverage | Add one architecture at a time; no model enters the catalogue without parity fixtures |

## Definition of done

`0.1.0` is not “the scaffolding is complete.” It is done when a new user can
install the package and obtain reference-matching forecasts from the pinned
TimesFM 2.5, Toto 2.0 4M, and Chronos-2 checkpoints through documented R
workflows, including Chronos-2 multivariate and covariate inputs, with the
results verified continuously by CI. A downstream `tsai` installation can
discover all three checkpoints offline, compare their capabilities and costs,
control download and reuse, handle failures by class, and compose them through
`TSFM()` without private APIs.
